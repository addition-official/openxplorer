## Summary

Pass 18 tested USB and other removable drives against Windows 11 with real drives: loop-backed FAT32, exFAT, NTFS and ext4 images handled by a real udisks2 2.10 and the GVfs udisks2 volume monitor, a 32 GB ext4 stick with 50,000 files, a read-only stick, an ISO image, one image split into three partitions, and a slow FUSE stick (about 2 MB/s) for pulling a drive out mid-copy. Input was real (xdotool/XTEST) on a private Xvfb, as an unprivileged user with a throwaway home. These are the fixes:

- **A crash-class bug in the progress window.** Clicking Skip, Try Again, Cancel or OK in the progress window left the window's keyboard on that button after its question had been taken out of the window. GTK then moved the keyboard on by itself after the next paint, walked the action's widgets while the old question was being freed, and read a freed widget (`Gtk-CRITICAL: gtk_widget_is_ancestor: assertion 'GTK_IS_WIDGET (widget)' failed`). It happened on about four answers in five while copying onto a USB stick that refuses some names (`a:b.txt`, `what?.txt` on NTFS). A read of freed memory can crash the app. The action now lets go of the keyboard before it hides or removes a question, or the whole action, that holds it.
- **A stick pulled out during a copy now says so, as Windows 11 does.** The question used to read "Item Not Found: Could not find this item. This is no longer located in <source folder>", blaming an item that was still where it was. It then asked again about every entry of the folder being copied. The engine now notes which drive held the destination folder when the run started. When that drive has left the mount table, or its folder answers with an error only a missing device gives, the item fails once with the question Windows 11 asked in a VM check: "Interrupted Action", "An unexpected error is keeping you from copying the file", "Error 0x800701B1: A device which does not exist was specified.", Try Again / Skip / Cancel. After Skip, nothing more is asked about the other files: a "Location is not available" box (red X, OK only) says "<folder>/ is unavailable. If the location is on this PC, make sure the device or drive is connected or the disc is inserted, and then try again. ...", and OK ends the copy. The partial staging file left on the stick is kept among the run's errors, but is not asked about on its own between Skip and that box. A folder deleted on a drive that is still mounted is still "Item Not Found".
- **A window on a stick that is pulled out goes to the Desktop.** As in Windows 11, every tab on a drive of this computer that goes away moves to the Desktop at once, without a message (Home when there is no Desktop folder). A disconnected share still shows "This location is unavailable" with Try again. A drive the window removes itself is left to that removal.
- **A drive still in use says so in Windows' words.** Eject, Safely remove or Disconnect on a drive a program still uses showed GTK's list of busy programs. It now shows Windows 11's box: a warning icon, "'<drive>' is currently in use.", "Save any open files on this disc, and then close the files or programs using the files before trying again." and "If you choose to continue, the files will be closed, which might cause data to be lost.", with Cancel (the default), Try Again and Continue. Continue removes the drive anyway, and Try Again asks the system again.
- **Optional: delete on removable drives permanently, as Windows does.** By default, Delete on a USB stick or SD card still moves the items to the drive's own Recycle Bin (`.Trash-<uid>`, OPS-018), as the owner decided. A new setting, Settings > Files & folders > Deleting > "Delete files on removable drives permanently (like Windows)", is off by default and stored only when on. With it on, Delete on a drive that can be ejected or powered off asks Windows 11's question, "Are you sure you want to permanently delete this file?" ("...these N items?" for several), Yes and No, and deletes the items for good, so they stop using the drive's space. Items elsewhere in the same selection keep their way.
- **Rename a file to other case on FAT32 or exFAT (better than Windows).** Renaming photo.txt to Photo.txt on a FAT32 or exFAT stick was refused with "An item named "Photo.txt" already exists", because the drive ignores case and sees the new name taken by the item itself. Windows 11 silently leaves the old name in that case (VM check, FAT32), so this goes beyond Windows. When no other item in the folder matches the new name in any case, the item goes through a private staging name and then to its new name. If the second step fails, it gets its old name back. The new name is never tried first, because exfat-fuse keeps answering that it exists for about a second. Undo works the same way.
- **A drive whose driver stopped answering says it is not ready.** An exFAT or NTFS stick whose FUSE driver quit (ntfs-3g and exfat-fuse do when their stick goes away) showed "Error opening directory '...': Transport endpoint is not connected". The page now reads "/media/demo/STICK is not accessible. The device is not ready.", as Windows says it of a drive that is not there. The system's words are under Details.
- **Rename a removable drive.** Rename was grayed out on every drive. On a removable drive the app can format, Rename (in the strip and the classic menu) now opens a Rename dialog with the volume label, fitted as it is typed to what the file system keeps. Rename sets the label through UDisks' `SetLabel`. FAT32 and ext4 are relabelled while mounted. exfatlabel finds a mounted exFAT stick busy, and ntfslabel refuses a mounted NTFS one, so those drives are unmounted, relabelled and mounted again, as a format does. The tabs on the drive follow it to the folder its new label gives it. A drive in use is refused with "The drive is in use. Close the files and programs using it, then try again.". Local Disk keeps Rename grayed out, now saying "Only a removable drive can be renamed here.". Windows renames a drive in place in This PC; here the menu opens a dialog.
- **A drive's crumbs start at This PC.** Inside a USB stick the address bar read "/ > media > user > STICK > Photos", and Up from the stick's root opened /media/user. As in Windows 11 ("This PC > USB Drive (E:) > Photos"), the crumbs inside a drive mounted on this computer now start at This PC and the drive's name as This PC shows it, and Up from its root opens This PC. Local Disk, network shares and "Show the full path" are unchanged.

Merged the lower-numbered jobs that change the same files: pass-9-scaling (with passes 1, 2, 5 and 8), network-like-windows, pass-3, pass-4, pass-6, pass-7, pass-10, pass-11, pass-12, pass-14, pass-15, pass-16 and pass-17. The copy question uses pass-15's `NOT_READY`, and three older tests now expect pass-15's Windows wording. pass-4's commit 5cb3a27c (computers under Network in the navigation pane) conflicts throughout the sidebar with network-like-windows, which does the same thing its own way. So pass-4 came in with that one commit reverted on top, and network-like-windows' version is kept.

After a Windows 11 VM check of these screens, checked by hand again with real input: a 2 MB/s FUSE stick pulled out while 400 files were copied onto it (the question, Skip, "Location is not available", OK ends the copy, and the window on the stick went to the Desktop); Disconnect through a real udisks2 while a program held a file on the stick (the box, Enter = Cancel, Try Again while busy and after closing the program, Continue); typing the gone stick's path ("can't find"); the new delete setting (found by searching Settings for "removable", then Delete on the stick asking each question, Yes deleting for good and No keeping the files); and photo to Photo, Undo, and a folder Trip to TRIP on exfat-fuse, plus the same rename on a fusefat FAT32 mount, where the unchanged code said the name was taken. Before that: live plug-in (This PC and the pane update with name, icon and capacity bar); copying onto NTFS and exFAT (names NTFS cannot hold get Try Again / Skip / Cancel); pulling a stick out mid-copy (forced lazy unmount, as udisks does on removal, and a killed FUSE driver); pulling it out while 500 thumbnails were being made; Disconnect while a program held a file (GTK's busy dialog names the program); renaming exFAT, NTFS, FAT32 and ext4 drives through the real UDisks; formatting FAT32 to exFAT; drive Properties; a read-only stick; an ISO; three partitions of one image; and 50,000 files on a 32 GB stick (first rows at about 2 s, all listed by about 5.6 s cold in a debug build; sorting, End and Ctrl+A each about a second). None of these logged a CRITICAL, panic or signal under `G_DEBUG=fatal-criticals`.

`native/parity/check.py`, the i18n check, rustfmt and the docs sync pass, and Clippy has no findings in the files this pass changed. On the final merged branch, every ox-app test ran isolated with `check.py`'s `run_isolated` as an unprivileged user: 2,808 passed. Six failed only because the USB stick from the live checks was still mounted, with a deleted file in its `.Trash-<uid>`; they pass with it unmounted. The other test executables pass except the root-only admin copy/delete tests and two tests that need the Python app's fixtures, which fail on unchanged main too. The Rename, Format and removable-drive Delete screenshots come from a local build that counts loop devices as removable. That one line was not committed, because loop devices are never removable.
