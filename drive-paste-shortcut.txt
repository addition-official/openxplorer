Copy (Ctrl+C, the menus' strip and classic row, and the command bar with a This PC tile selected) is enabled on drives, and Cut stays unavailable. Paste and every drop turn each drive This PC lists into a shortcut, the app's existing symlink shortcut named 'Local Disk - Shortcut', then '(2)', so a drive's contents are never copied. Windows' 'Local Disk (C:)' becomes 'Local Disk' because the app shows no drive letters. Dragging a drive shows 'Create link in <folder>', and a right-drag offers only 'Create shortcuts here'. Sources: dragging a drive defaults to a link (MakeUseOf guide; ReactOS CFSDropTarget 'Don't copy a drive by default', bug CORE-17871); the 'can't create a shortcut here, place it on the desktop' question belongs to Create shortcut inside This PC (KB 179513; Microsoft Q&A for Windows 11), not to a paste into a folder, so nothing is asked. No published source confirms that a plain paste of a copied drive makes a shortcut (an informal Windows 10 report says nothing happens), so the task's stated Windows 11 behavior was followed. Existing behavior, not changed: clicking a sidebar row moves keyboard focus to the file list, so Ctrl+C on a sidebar drive works with the row focused (Tab, F6 or Shift+F6); opening the shortcut browses the drive under the link's path instead of jumping to the drive. A separate bug found in QC: after a drop into the file list and a visit to This PC, the file list ignores the next drag (GTK 'self->drop == drop'). It reproduces with an ordinary folder, so the right-drag check runs from a fresh start. Two earlier full runs were stopped by a crash on a GLib worker thread (a libgtk segfault and a GLib trap); it did not recur in the final full run or in window::tests, and its cause is unknown.
