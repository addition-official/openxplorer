The Preview pane now shows text (first 1 MB, fixed-width, wrapping), PDF pages (pdftoppm in the existing bubblewrap thumbnailer sandbox, 4 pages per run, up to 50), pictures fitted to the pane, and "No preview available." for folders, several items, binaries, other types and network files with network previews off; nothing selected shows "Select a file to preview.". Audio/video unchanged. Undecidable choices, made the most Windows-like and safe way: (1) picture_guard (#285) is not on main, so pictures use a header check with the same 64-megapixel cap, then gdk-pixbuf decoding to the pane's size; switch to picture_guard once #285 merges. (2) No new link dependency: poppler-glib is not a dependency, so PDFs use the poppler-utils program pdftoppm inside bubblewrap; with no bwrap or no pdftoppm a PDF says "No preview available." (Windows without a PDF previewer says the same). Packages may want to Recommend poppler-utils and bubblewrap. (3) Network files are read only through a local (FUSE) path, so with network previews on but no gvfs-fuse, a share's file still says "No preview available.". (4) Windows' text font is not documented; the task asked for monospace, so the pane uses the desktop's monospace font at the app's text size. (5) Several selected items: no source found; chose "No preview available." as the task suggested. (6) Lines over 4,096 characters are broken into paragraphs so a minified file cannot stall layout. Run as user oxtest on Xvfb with xdotool; captures 1x and 2x, light and dark; the *-strip.png files show the pane for every case side by side. Tests run: preview_page (4), preview_pane (5), details_pane, details_preview, environment, thumbnails by name: all pass except thumbnails::thumbnailers::tests::a_sandboxed_thumbnailer_sees_only_its_item, which fails the same way on upstream main in this container (root + bubblewrap). rustfmt clean; clippy (1.97.0) shows the same 15 pre-existing warnings as main, none in changed code. parity/check.py passes.
