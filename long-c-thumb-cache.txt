HEAD: long-c-thumb-cache 00b00987
QUESTION: Thumbnails of files deleted or sent to the Recycle Bin stay in ~/.cache/thumbnails (the standard says to remove them; GNOME and KDE mostly don't; Windows keeps them in thumbcache_*.db, a known privacy complaint). This branch only moves the entries of files the app moves or renames. Should it also remove the entries of files it deletes or recycles?
NOTE: A revisited folder shows its thumbnails at once, as Windows does from thumbcache, from the freedesktop shared cache (normal, large, x-large, xx-large; MD5 of the URI).
- Lookup: the app reads the cache first, itself. It parses Thumb::URI, Thumb::MTime and Thumb::Size (when present) from the PNG text chunks in safe Rust, without decoding. A larger size stands in for a smaller one. GIO's thumbnail::* query is now used only for files without a known time.
- Batched reads: current entries are decoded in the sandboxed decoder pool, 12 per request to one decoder, each answer handed back as it comes. A crashing picture is refused alone and the rest of its batch goes to a new decoder.
- Memory: a 64 MB LRU of shown thumbnails (kept at the size shown, about 2,700 Large-icon photos), checked against mtime and size, draws a same-session revisit on the tile's first frame, also with network previews off (the default) however long ago the folder was found local.
- No icon flash: the cache's entry names are listed in the background once a view with thumbnails is set up (as 128-bit numbers: 5.6 MB for 200,000 entries), so a tile whose entry exists hides its type icon (250 ms at most) until the read lands. Decoders start in the background then too. Thumbnails show as soon as they are read; a custom icon found later replaces one.
- Generation: off the main thread, on one fewer slot than the processors (2 to 3, was 2), with tiles on the screen first (GTK binds about 190 for 30 visible). A cell counts as on screen only once it is laid out. A new photo costs 1 decode instead of 3.
- Writes: 0600 temp file (O_EXCL, O_NOFOLLOW) in 0700 folders, renamed into place, with Size and Mimetype keys.
- Failures: damaged pictures, and files a desktop thumbnailer ran to the end on and gave up on, go to thumbnails/fail/openxplorer. With gnome-thumbnail-factory's failures, they are not retried until the file changes.
- Moves: a file the app moves or renames (via the undo journal, so Undo and Redo too), and every file of a moved folder up to 5,000, keeps its entries. The keys are rewritten with the pixels untouched; an entry from another version is left alone.
- Review fixes (an independent read of the whole diff):
  - a tile rebound while its thumbnail was being made could show the previous item's picture, because glib detaches a task whose JoinHandle is dropped; fixed and tested
  - a custom icon that failed to decode hid the thumbnail
  - keys are now also read from zTXt/iTXt (Qt compresses values of 40 characters or more), within 64 KB inflated
  - batched moves read every entry before writing (name swaps)
  - moves are not followed over network file systems
  - a picture a decoder refuses is retried once in another decoder before being recorded as damaged, since a decoder out of CPU time refuses the same way
- Policy: "Always show icons" starts and reads nothing. x-large is used for Extra large icons at 2x, and the service is asked for it only if GetFlavors lists it.
- Cleanup: left to the desktop. The Interface guide (docs.json, regenerated) says so, as Windows leaves it to Disk Cleanup / Storage; no button added.
- Tools: OX_THUMBNAIL_TRACE plus native/tools/thumbnail-bench.py measure all of this.
- Cache layout is generic for long-d-doc-previews: anything written through writer::save_thumbnail or the desktop thumbnailers gets the same keys and is read back through the same batched path.
- Root: check.py stops at display_scale in this container because the app refuses to run as root ("Run OpenXplorer as your regular desktop user, not with sudo"), so every test binary was also run through check.py's run_isolated as an unprivileged user.
